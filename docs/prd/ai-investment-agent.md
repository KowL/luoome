## 1. 文档结论

luoome 的 Agent 不是一组拥有独立数据库和重复业务逻辑的“虚拟员工”，而是同一套
tool/workflow 能力上的智能交互与编排层。

```text
用户意图
  → Agent 理解与计划
  → 从白名单选择 tool
  → 获取结构化事实
  → 交叉验证与披露缺失
  → 输出回答、Advice 或待确认草案
```

产品上可以使用“研究助手、风险助手、复盘助手”等角色表达，但实现上优先采用：

- 一个统一 Agent Runtime；
- 按场景选择 system prompt、工具白名单、预算和输出 schema；
- 领域逻辑继续由 tools/core 承担；
- 稳定定时任务继续由 workflow 承担。

首期不建设 Agent 市场、远程 Agent 注册中心或多 Agent 社交式讨论。

## 2. 产品定位

### 2.1 一句话定位

> 一个能调用 luoome 真实能力、展示证据、理解权限边界并把复杂操作变成可确认草案的投资研究助手。

### 2.2 Agent 与普通聊天的区别

Agent 必须能：

- 识别用户问题对应的股票、账户、Strategy、Watchlist、AlertPlan 和时间范围；
- 自主选择多个只读工具并使用工具结果继续推理；
- 区分事实、观点、Advice 和写操作；
- 说明数据缺失、降级来源及结论有效期；
- 将本地写操作生成草案，等待用户确认；
- 保留工具调用轨迹，支持审计和故障定位。

只有自然语言回答、没有工具证据的功能不应被称为 luoome Agent 能力。

## 3. 当前基础

当前系统已经具备：

- 由 Zod schema 派生的统一 tool registry；
- `read / write / external / advice / trade` 副作用分级；
- AI SDK Provider Registry 与 SDK 无关的 `AgentRuntimeLike`；
- `agent_run` 和 Web 对话使用显式能力白名单；
- 多轮 tool loop；
- Web 写操作的 draft-and-confirm；
- 持仓、行情、现有战法/分组/盯盘、研究档案、报告和 Advice 工具；
- workflow 运行记录与结构化报告。

当前缺口主要是产品层，而不是再引入一套 Agent 框架：

- 场景入口和能力边界不够清晰；
- 长任务的计划、进度、部分失败和结果回看体验不足；
- Agent 产出的研究结论未统一落到研究档案或 Advice；
- 权限解释和草案确认需要更一致；
- 缺少按场景评估 Agent 质量的标准。

## 4. 产品原则

### 4.1 一个运行时，多种角色视图

“研究 Agent”“风险 Agent”“复盘 Agent”是能力配置，不默认成为独立进程或新领域实体。
只有当角色拥有独立权限、状态、生命周期或部署边界时，才评估独立 Agent。

### 4.2 Tool 是能力事实来源

- Agent 通过 registry discovery 获取能力，不硬编码另一份工具清单。
- 同一业务操作在 Web、CLI、MCP 和 Agent 中使用同一 tool。
- Agent 不直接访问 repository、数据库或 adapter。
- workflow 不包装成可被 Agent 递归调用的普通 tool。

### 4.3 自动规划不等于自动副作用

| 副作用 | Agent 行为 |
|---|---|
| `read` | 可在预算内自动调用 |
| `advice` | 可按用户明确的分析意图调用，结果遵守 Advice 契约 |
| `external` | 按能力和用户设置控制，展示来源与失败 |
| `write` | 先生成草案，由用户确认后调用真实工具 |
| `trade` | 不向 Agent 暴露 |

### 4.4 证据优先

Agent 输出重要判断时要区分：

- 已由 tool 返回的事实；
- 基于多个事实作出的推断；
- 用户或来源中的观点；
- 数据缺失导致的未知项；
- 结构化 Advice。

不得把模型先验包装成已查询到的本地事实。

### 4.5 确定性任务留给 workflow

开盘报告、盘中盯盘、盘后同步、Strategy 与 Watchlist 同步等固定流程由 workflow 执行。Agent 适合开放式
研究和交互式编排，不替代可重复、可测试的任务管道。

## 5. 场景化能力

### 5.1 投资经理入口

负责识别意图、选择场景并汇总结果。典型问题：

- “我的投资体系今天发生了什么？”
- “这条预警值得进一步研究吗？”
- “我持仓里哪些风险需要先处理？”

它不创建新的“InvestmentManager”持久化实体。

### 5.2 股票研究

可调用：

- 股票搜索与行情；
- 日线和技术指标；
- StrategyResult 和 StrategySignal；
- 研究笔记、公司事件；
- 所属 Watchlist、提醒与历史 Advice；
- 数据来源状态。

输出分两种：

1. 事实型研究摘要：可保存为 `ResearchNote` 草案。
2. 决策型结论：必须生成结构化 `Advice`。

### 5.3 持仓与风险

读取账户、持仓、行情、成本、集中度、相关事件和历史 Advice，回答：

- 风险来自哪里；
- 哪些数据支持该判断；
- 哪些风险无法评估；
- 是否值得生成一次新的持仓 Advice。

调仓比例只能作为 Advice，不是订单或自动持仓修改。

### 5.4 策略研究

帮助用户：

- 把自然语言投资方法映射为 Strategy DSL 草案；
- 解释 universe、因子、筛选、评分、信号、风控和评估口径；
- 解释哪些条件当前可确定性执行；
- 生成 Strategy 新版本并试算；
- 在用户确认显式 Strategy→Watchlist 订阅后，将 StrategyRun 结果投影到统一 Watchlist；没有订阅时只能生成手工加入或订阅草案；
- 对历史信号、候选变化和真实后续表现做描述性复盘。

Agent 不在对话中即时发明未注册的因子，也不把一次生成的 Strategy 直接投入定时运行。
草案必须通过 schema、数据依赖、时间切片和样本试算校验，并由用户确认发布。

### 5.5 复盘

汇总：

- AdviceOutcome；
- SignalObservation；
- Trade 和 Holding 变化；
- 研究假设版本；
- 报告和数据缺失。

Agent 可以提出改进草案，但要避免把小样本相关性称为策略失效或因果规律。

## 6. 路由与规划

### 6.1 路由

优先使用一个轻量路由步骤识别：

- 场景：研究、持仓、观察、报告、复盘、设置；
- 主体：stock/account/group/plan/report；
- 是否需要 Advice；
- 是否涉及写操作或外部调用；
- 缺少哪些必要标识。

简单查询直接执行，不为了展示“智能”强制拆成多个角色。

### 6.2 计划

满足以下任一条件时展示计划：

- 需要三个及以上数据域；
- 预计超过一次模型调用；
- 包含外部数据或长耗时扫描；
- 可能产生待确认写操作。

计划应展示目标和进度，不暴露内部思维链。每一步记录工具名、状态、耗时和可公开摘要。

### 6.3 部分失败

Agent 不能因为一项数据失败就伪造完整答案，也不应在仍有价值时丢弃全部结果。输出需包含：

- 已完成的维度；
- 失败或不可用的维度；
- 对结论的具体影响；
- 是否值得重试。

## 7. 交互设计

### 7.1 回答结构

复杂投资问题默认按以下层次呈现：

1. 结论摘要；
2. 关键事实与数据时间；
3. 支持证据与反证；
4. 风险和未知项；
5. 可选下一步。

只有真实 Advice 才展示 decision、confidence、validUntil 和标准免责声明。

### 7.2 操作草案

对创建 Strategy、Watchlist、AlertPlan、研究笔记等写操作，草案卡片必须展示：

- 将创建或修改什么对象；
- 用户原始意图如何映射为字段；
- 系统补充的默认值；
- 未支持或有歧义的条件；
- 取消、编辑和确认操作。

确认只授权当前草案，不授权后续同类操作。

### 7.3 长任务

全市场扫描或多源研究应支持：

- 可见的运行状态；
- 超时或预算上限；
- 取消；
- 部分结果；
- 完成后可回看的产物或 workflow run。

## 8. 外部能力边界

未来如接入第三方研究或数据能力，优先把它们建模为 adapter 或 tool provider，而不是允许远程
Agent 绕过 luoome 契约。

外部能力必须声明：

- capability 和版本；
- 输入输出 schema；
- 数据来源与时间；
- 副作用等级；
- 权限和凭证范围；
- 超时、费用及失败语义。

首期不做：

- Agent 商店和付费分发；
- 第三方 Advice 自动融合成 luoome Advice；
- 外部 Agent 直接写数据库；
- 外部 Agent 获取完整账户或私人研究数据；
- 跨用户分享“高收益 Agent”。

## 9. 分期

### Phase 0：统一现有体验

- 收口研究、持仓、观察和复盘四类场景提示词与白名单。
- 统一事实、推断、未知项和 Advice 的显示。
- 统一 write 草案卡片和确认语义。
- 工具轨迹可查看但默认折叠。

### Phase 1：可追溯研究助手

- 股票与持仓研究可跨工具完成。
- 结果可保存为 ResearchNote 草案或 Advice。
- 引用研究档案、触发、报告时可返回具体对象。
- 部分失败和数据健康状态进入最终回答。

### Phase 2：闭环复盘助手

- 串联研究假设、Advice、Trade、Outcome 和 SignalObservation。
- 基于真实样本生成行为复盘。
- 用户确认后生成 Strategy、Watchlist 或 AlertPlan 的修改草案。

### Phase 3：受控外部能力

只在有明确需求时接入受 schema、权限和 provenance 约束的外部数据/研究工具。是否需要独立
Agent 注册协议，届时依据实际的跨进程生命周期决定。

## 10. 验收标准

- 同一问题重复运行时，确定性事实来自 tool，不依赖模型记忆。
- Agent 无法调用 trade 工具，也无法绕过 write 确认。
- 每个 Advice 都满足证据、反证、风险、免责声明和有效期约束。
- 数据源失败时明确披露影响，不生成伪完整答案。
- 场景角色不复制领域逻辑或持久化模型。
- 关键场景有固定评测集：工具选择正确率、schema 成功率、引用完整率、越权率和人工可用率。
