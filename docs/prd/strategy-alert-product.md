# 策略预警产品文档

> 状态：产品方向已确认；Phase 1 已实现（2026-07-25）
> 日期：2026-07-24
> 参考：旧项目 `ruo` 的策略监控与主动预警实现、luoome v0.8.0 的股票分组与盘中盯盘能力
> 产品边界：本地单用户、Web 为主入口、CLI/MCP 为高级入口；只提醒和辅助决策，不自动下单
>
> 后续能力：公司事件、研究档案、数据新鲜度和真实信号复盘见 [ruo 能力迁移产品设计文档](./ruo-feature-migration-product-design.md)。

## 1. 文档结论

luoome 不应移植 ruo 的“策略配置系统”，而应把现有的“股票分组 + 盯盘方案 + 盯盘触发”升级为一套更易理解、更可靠的**策略预警闭环**：

```text
选择监控对象       定义何时提醒       可靠执行          解释与处置         复盘
股票分组      →    盯盘方案      →   Watch Runner  →   预警事件      →   结果反馈
看哪些股票         哪些条件触发       交易时段扫描       为什么触发         是否有用
```

面向用户仍使用“分组”和“盯盘方案”，避免再引入一个与现有概念重叠的“策略”实体；“策略预警”是这一整条产品能力的统称。

首期重点不是增加更多技术指标，而是补齐四件事：

1. 让用户能快速创建正确的预警，而不是面对原始 DSL 和技术参数。
2. 从“条件持续成立就重复提醒”升级为可理解的事件触发与恢复机制。
3. 让每条预警包含上下文、证据、优先级和可执行的下一步。
4. 建立预警效果复盘，回答“哪些规则对我有用、哪些只是在制造噪声”。

## 2. 背景与问题

### 2.1 ruo 做过什么

ruo 的策略预警能力先后出现过三种形态。

#### 形态 A：浏览器内策略引擎

- 用户为单只股票创建“持仓策略”或“个股追踪”。
- 支持价格上涨/下跌、价格区间、放量、首板、连板、持仓盈利/亏损等条件。
- 多条件支持 `AND` / `OR`。
- 浏览器每 30 秒拉取一次东方财富行情并执行条件判断。
- 触发后发送浏览器通知和飞书 Webhook。
- 以 5 分钟时间桶做内存去重。

优点是配置直观、反馈快；主要问题是：

- 页面隐藏或关闭后暂停，不能承担可靠盯盘。
- 去重只在内存中，刷新或重启后丢失。
- `volume_spike`、`continuous_board` 等部分规则实际是简化占位，不符合界面表达。
- 浏览器直连飞书 Webhook，密钥和跨域边界不理想。
- 一条策略只绑定一只股票，不利于复用一组股票和一套规则。

#### 形态 B：统一信号与订阅管道

ruo 曾将 strategy、pattern、portfolio 三类信号统一为：

```text
SignalEvent → StockAlert → UserAlertDelivery
```

并计划使用 Redis Streams 完成标准化、订阅匹配和按用户推送，统一置信度、冷却时间、每日上限、排除股票等过滤条件。

这套设计解决了多用户、多信号源和多通道送达问题，但对本地单用户的 luoome 明显过重：它引入独立 Worker、Redis、扇出表和用户级送达状态，运维成本大于产品收益。

#### 形态 C：AI 主动持仓预警

ruo 后来弱化用户配置，按固定阈值扫描持仓，识别大涨、大跌、涨停、跌停、炸板、断板、热点关联，并直接生成站内消息；同一用户、股票、类型每天只通知一次。

它说明“自动盯持仓、只在重要时打扰”有产品价值，但固定阈值和 AI 自主判断都不能完全替代用户意图。用户仍需要明确表达自己的成本线、关注周期和交易风格。

### 2.2 luoome 当前基础

luoome 已经具备一条可用的盯盘主链：

- `StockGroup` 回答“看哪些股票”，支持 manual、holdings、formula、llm 四类 resolver。
- `StockPool` 在产品层称为“盯盘方案”，回答“什么情况提醒”，引用一个分组。
- 当前规则有 tactic、cost-threshold、price-change。
- `intraday-watch` 在交易时段批量拉行情、执行规则、做持久化 cooldown、写入 `WatchTrigger` 并发送飞书或日志通知。
- `WatchRun` 记录每轮心跳，即使没有触发也能判断系统是否健康。
- Web 已支持分组和盯盘方案的创建、编辑、启停、删除、单轮试跑和触发查看。
- 建议、预警与真实交易严格分离。

当前缺口主要在产品语义和闭环，而非执行骨架：

- 规则类型少，且 `price-change` 只支持绝对涨跌幅，无法表达方向。
- 多条规则固定为“任意命中”，不能表达简单的组合条件。
- cooldown 抑制重复通知，但没有“首次进入条件 / 持续命中 / 恢复 / 再次进入”的事件语义。
- `WatchTrigger` 只有 `notified: boolean`，无法区分未要求通知、冷却抑制、发送成功、发送失败。
- 通知是按方案聚合的技术摘要，缺少优先级、相对成本、规则名称和下一步入口。
- 触发历史可审计，但没有已读、处理、忽略、有用/无用等用户反馈。
- tactic 可查询和运行，但普通用户创建预警时仍需理解 tactic id、score 和 resolver 差异。

## 3. 产品目标

### 3.1 一句话定位

> 让用户用一句投资意图或一个简单模板建立盯盘规则，在真正值得关注时收到可解释、可处置、可复盘的提醒。

### 3.2 目标用户

- 没时间持续看盘，但希望守住止盈止损的个人投资者。
- 有明确交易方法，希望批量监控候选股的活跃交易者。
- 希望使用自然语言和模板，而不是编写公式或 DSL 的普通用户。

### 3.3 核心价值

| 用户问题 | 产品回答 |
|---|---|
| 我应该盯哪些股票？ | 用分组表达持仓、手工候选、公式筛选或 LLM 选股结果 |
| 发生什么才值得叫我？ | 用模板化规则、组合条件、优先级和冷却表达 |
| 系统真的在工作吗？ | 展示 watch 心跳、行情新鲜度、分组 stale 和本轮评估结果 |
| 为什么提醒我？ | 保留触发时行情、基准值、条件结果和战法证据 |
| 我接下来该做什么？ | 查看持仓/个股、生成一次建议、暂时静默或调整规则 |
| 这套预警是否有用？ | 记录处置和后续表现，统计噪声率与有效率 |

### 3.4 非目标

- 不自动下单，不提供自动跟单。
- 不在首期建设多租户订阅扇出、Redis Streams 或独立预警微服务。
- 不把 LLM 放入每分钟的高频判定链路。
- 不在首期建设完整的量化回测平台。
- 不承诺“命中等于盈利”，预警只表示条件成立。

## 4. 产品原则

### 4.1 规则负责确定性，AI 负责降低配置和理解成本

- 盘中判定由确定性规则完成，结果可复现、成本可控。
- AI 可将自然语言转换为分组和盯盘方案草案，但必须由用户确认后保存。
- AI 可在用户点开重要预警时生成一次结构化建议，不在每轮扫描中调用。

### 4.2 对象和条件分离

- 股票分组只维护成员。
- 盯盘方案只维护规则、触发策略、冷却和通知偏好。
- 同一分组可复用多套方案，例如“持仓风控”和“持仓趋势机会”。

### 4.3 触发是事实，通知是触发后的送达结果

即使用户关闭通知、处于冷却期或飞书发送失败，触发事实仍应落库；通知状态不能再只由一个 `notified` 布尔值表达。

### 4.4 默认少打扰

- 默认采用“进入条件时提醒”，条件持续成立不重复轰炸。
- 默认设置冷却和每日上限。
- 系统级故障与行情异常不能伪装成“没有触发”。

### 4.5 预警不等于建议，更不等于交易

- 预警原样陈述“哪个条件成立”。
- 建议需要单独生成，并带反证、风险、免责声明和有效期。
- 任何预警或建议都不能自动触发交易。

## 5. 领域模型

### 5.1 产品概念

| 产品概念 | 当前实现 | 本期处理 |
|---|---|---|
| 股票分组 | `StockGroup` | 保留 |
| 盯盘方案 | `StockPool` | 保留内部命名；继续使用面向用户的“盯盘方案” |
| 触发规则 | `WatchRule` | 扩展 |
| 预警事件 | `WatchTrigger` | 扩展事件和送达语义 |
| 运行心跳 | `WatchRun` | 保留 |
| 通知记录 | `Notification` | 与触发建立明确关联 |
| 处理反馈 | 暂无 | 新增轻量反馈 |

不新增独立的 `Strategy` 实体。用户口中的“策略”可以落为：

- 一套选股逻辑：formula 分组；
- 一套盯盘条件：盯盘方案；
- 二者组合：一个完整的“策略预警”。

### 5.2 规则类型

#### 当前规则

| 规则 | 含义 | 建议调整 |
|---|---|---|
| cost-threshold | 相对持仓成本的止盈/止损 | 保留，拆分展示止盈与止损的独立命中原因 |
| price-change | 相对昨收的绝对变动 | 增加方向：上涨、下跌、任一方向 |
| tactic | 战法信号分数达到阈值 | 保留，界面显示战法名、方向和默认阈值 |

#### P1 新增规则

| 规则 | 用户表达示例 | 说明 |
|---|---|---|
| price-level | “比亚迪突破 350 / 跌破 310” | 支持 above / below，采用穿越触发（边沿语义，见 §5.4） |
| volume-ratio | “成交量达到 20 日均量 2 倍” | 使用真实成交量与均量，不复用价格涨幅近似；口径为量比：当日累计成交量 /（20 日日均量 × 当日已交易时间占比），避免上午半日量与全日均量直接比较 |
| drawdown-from-high | “从近 20 日高点回撤 8%” | 适合移动止盈；高点口径为近 20 个交易日 daily bar 最高价与当日盘中最高价的较大者 |

#### P2 候选规则

- 涨停、炸板、断板等 A 股事件规则。
- 均线交叉、振幅、换手率等常用指标规则。
- 热点/板块关联规则，但必须先解决稳定的板块数据来源。
- 公告、财报、新闻等事件规则，作为低频外部信号，不进入首期行情热路径。

### 5.3 组合条件

首期不提供任意嵌套的规则树，只提供两种方案级逻辑：

- `ANY`：任一规则进入触发状态就产生预警，保持当前默认行为。
- `ALL`：所有规则在同一评估窗口成立时产生一条组合预警，不做跨窗口拼接。

每条规则仍保存独立求值结果和证据。已触发的组合预警展示全部已满足条件及其证据；“哪些条件已满足、哪些尚未满足”的差量信息属于试跑与评估详情的展示（例如“还差放量条件未满足”），帮助用户理解为什么没触发，不出现在已触发的预警里。

复杂嵌套条件继续由 tactic DSL 承担，避免在 Web 再造一套表达式语言。

### 5.4 触发模式

规则按求值语义分为两类：

- **持续条件型**（cost-threshold、price-change、volume-ratio、drawdown-from-high、tactic）：条件在一段时间内持续成立或不成立，适用完整状态机。
- **穿越型**（price-level，以及未来的均线交叉等）：语义本身就是边沿（从下向上穿过阈值），天然等价于“进入条件时”。方案选择 `repeat` 或 `daily-first` 时，穿越型规则仍只在穿越发生的那一轮触发，不随模式重复提醒。

每个方案选择一种触发模式：

| 模式 | 行为 | 适用场景 |
|---|---|---|
| 进入条件时 | false → true 时提醒；持续 true 不重复 | 默认，大多数策略 |
| 每次满足 | 满足后按 cooldown 重复提醒（仅对持续条件型规则生效） | 高频跟踪强提醒 |
| 每日首次 | 每个交易日第一次满足时提醒 | 日涨跌、热点类 |

为了支持“进入条件时”，系统需要保存规则状态：

```text
inactive → active    产生 triggered
active   → active    不提醒
active   → inactive  记录 recovered，可选通知
inactive → active    再次产生 triggered
unknown              行情缺失/求值失败时保持原状态，不产生边沿
```

状态生命周期约定：

- **初始化**：规则的持久化状态不存在时（新建方案、新增规则、股票新进入分组），首轮评估只写入状态，不产生 triggered。用户保存前可通过试跑看到当前命中情况，避免新方案一启用就被存量命中轰炸。
- **成员变动**：状态按 `(poolId, stockId, ruleId)` 保存。股票退出分组期间暂停评估、状态保留；重新进入时从保留的状态继续边沿判断。
- **recovered 送达**：默认不通知；开启后与普通预警走同一 cooldown 和每日上限，默认优先级为“普通”。

这比仅依赖 cooldown 更符合用户对“突破”“跌破”和“重新满足”的理解。

### 5.5 预警优先级

优先级为**规则级字段**，方案可设默认值；规则未设置时取方案默认值，方案也未设置时按规则种类推导：

- 紧急：止损（cost-threshold 止损侧）、跌停、重大风险；默认立即推送。
- 重要：止盈（cost-threshold 止盈侧）、价格突破/跌破、高分战法；默认推送。
- 普通：日内波动、观察信号、恢复通知；可只进站内历史或聚合摘要。

优先级只影响展示和送达，不改变规则是否成立。

## 6. 核心用户流程

### 6.1 从模板创建

1. 用户进入某个分组详情。
2. 点击“添加盯盘方案”。
3. 选择模板：
   - 持仓止盈止损；
   - 价格突破/跌破；
   - 日内异动；
   - 战法买点；
   - 战法风险；
   - 自定义组合。
4. 系统根据分组类型预填参数。
5. 用户查看示例：“若现在运行，过去一轮会命中几只股票”。
6. 用户确认通知方式、冷却和启用状态后保存。

模板只生成普通实体，不形成另一套模板运行时。

### 6.2 用自然语言创建

示例：

> 盯住我的持仓，亏损 7% 或量价背离超过 70 分时提醒我，30 分钟内不要重复。

AI 生成待确认草案：

```json
{
  "groupId": "holdings-default",
  "logic": "ANY",
  "rules": [
    { "kind": "cost-threshold", "stopLossPct": 0.07 },
    { "kind": "tactic", "tacticId": "volume-price-divergence", "minScore": 70 }
  ],
  "cooldownMinutes": 30,
  "triggerMode": "on-enter"
}
```

草案页面必须：

- 用自然语言复述最终规则；
- 标出系统补充的默认值；
- 对不支持或有歧义的条件明确提示；
- 由用户确认后才调用写工具。

### 6.3 收到并处理预警

预警卡片至少展示：

- 股票代码与名称、所属方案；
- 优先级和方向：买入观察 / 卖出观察 / 仅关注；
- 一句话原因；
- 当前价、基准价、涨跌幅、相对成本收益；
- 1–3 条证据和数据时间；
- 通知状态；
- 操作：查看股票、查看持仓、生成建议、静默、调整规则、标记已处理。

“生成建议”单独调用 advice 能力。建议必须完整展示反证、风险、免责声明和有效期。

### 6.4 复盘与降噪

用户可对预警做轻量反馈（记录在该条预警事件上）：

- 有用；
- 无用；
- 已处理；
- 忽略。

另提供“规则太频繁”作为预警卡片上的快捷操作：不作为一种反馈状态落库，而是直接带用户跳到对应方案的规则编辑入口。

系统提供 7 日 / 30 日统计：

- 触发数、实际通知数、冷却抑制数、发送失败数；
- 已处理率、有用率、无用率；
- 按方案、规则和股票分布；
- 同类预警平均间隔；
- 可选：触发后 1 日 / 5 日价格表现。

首期只做客观统计，不自动把收益归因为某条策略。

## 7. 页面与交互

### 7.1 仪表盘

在现有 watch 健康度和最近触发上增加：

- 今日紧急 / 重要 / 普通预警数量；
- 发送失败与数据异常提示；
- 待处理预警；
- “噪声最高的方案”提示，仅在样本充足时展示。

### 7.2 分组详情

延续当前“成员与盯盘方案”一体化设计：

- 上半区展示分组成员、来源、刷新状态。
- 下半区展示引用该分组的盯盘方案。
- 新建方案优先走模板，保留高级编辑入口。

### 7.3 方案编辑器

基础区：

- 名称、说明、成员分组、启停。

条件区：

- 模板化规则卡片；
- `ANY` / `ALL`；
- 每个字段带单位、默认值、数据口径说明；
- tactic 用名称和说明选择，不要求用户填写 id。

通知区：

- 优先级；
- 触发模式；
- cooldown；
- 每日通知上限；
- 通知通道；
- 可选恢复通知。

验证区：

- “立即试跑”；
- 显示评估股票数、命中数、示例证据；
- 试跑只记录，不发送，不占用正式通知 cooldown。

### 7.4 预警中心

不新增主导航信息孤岛。仪表盘保留最近预警，分组详情展示相关预警；当触发量增长后再增加二级“全部预警”页。

筛选项：

- 时间、方案、分组、股票、规则、优先级；
- 已通知 / 被抑制 / 发送失败；
- 待处理 / 已处理；
- 有用 / 无用。

## 8. 通知策略

### 8.1 默认策略

- 紧急和重要：实时发送。
- 普通：默认仅记录，或在 15 分钟窗口内按方案聚合。
- 同一方案、股票、规则遵循触发模式和 cooldown。
- 每个方案默认每日最多 20 条外部通知，用户可在合理范围内调整。
- 另设全局兜底：全部方案合计每日最多 50 条外部通知，防止多方案叠加轰炸；达到全局上限后仅记录不再外发，并在仪表盘提示。
- 行情源完全失败时发送一次系统健康提醒，不产生业务预警。

### 8.2 通知文案

建议格式：

```text
[重要][卖出观察] 宁德时代 触发“持仓风控”

原因：现价 182.30，较成本 198.20 下跌 8.02%，已达到止损线 7%。
证据：行情时间 10:32:01；规则阈值 -7%；当前 PnL -8.02%。

这是规则触发提醒，不构成投资建议，也不会自动下单。
```

聚合通知必须保留每只股票的方向和核心原因，不能只有“共 N 条触发”。

### 8.3 送达状态

建议将送达状态显式化：

- `not-requested`：试跑或普通预警只记录；
- `suppressed-cooldown`：冷却抑制；
- `suppressed-daily-limit`：每日上限抑制；
- `pending`：等待发送；
- `sent`：发送成功；
- `failed`：发送失败；
- `fallback-log`：外部通道未配置，已降级日志。

`WatchTrigger.notified` 可在兼容期保留，但 Web 和新接口使用上述状态，不再反推布尔值含义。

## 9. 与当前系统的结合方案

### 9.1 保留

- `StockGroup` 及成员快照；
- `StockPool` 持久化表和 CRUD tool；
- `intraday-watch` workflow；
- `luoome watch` / `luoome start`；
- `WatchRun`；
- `WatchTrigger` 的行情快照和证据；
- `Notification` 与飞书/log adapter；
- tactic DSL 与 `run_tactic`；
- Web mutation 鉴权和试跑入口。

### 9.2 扩展

建议以兼容字段演进，不新建平行系统。

#### StockPool / 盯盘方案

新增：

- `logic: 'ANY' | 'ALL'`，默认 `ANY`；
- `triggerMode: 'on-enter' | 'repeat' | 'daily-first'`，默认 `on-enter`；
- `priority`：方案级默认优先级，规则未设置时使用；
- `dailyNotificationLimit`；
- `notifyOnRecovery`；
- 通知偏好。

#### WatchRule

新增：

- 稳定 `id` 字段（`rules[].id`）：创建时生成，编辑规则参数保持不变，删除后重建生成新 id、不复用；
- price-change 的 direction；
- price-level；
- volume-ratio；
- drawdown-from-high。

存量 pool 的 rules 没有 id，启动时做幂等迁移补齐（参照 v0.6 分组迁移的做法）。

#### WatchTrigger

新增：

- 触发类型 `triggered | recovered`；
- 优先级（落库时为生效值，不再依赖反推）；
- `ruleId`：规则实例标识，不能只用 `ruleKind` 区分同类多规则；
- `deliveryStatus`；
- `notificationId?`；
- 条件求值快照；
- 用户反馈状态。

当前 cooldown key 是 `(poolId, stockId, ruleKind)`。当一个方案允许两条同类规则后会互相错误抑制，必须改为 `(poolId, stockId, ruleId)`。

cooldown 兼容：迁移时为历史 `WatchTrigger` 回填 `ruleId`——当对应 pool 内该 `ruleKind` 的规则只有一条时可唯一映射，直接回填；存在多条同类规则的存量数据无法唯一映射，置空并接受这部分池在升级后冷却重置一轮（持续成立的条件可能补发一次通知）。新评估一律使用 `ruleId`。

#### 规则状态

新增轻量 `WatchRuleState` 持久化：

- poolId、stockId、ruleId；
- active；
- firstTriggeredAt、lastEvaluatedAt、lastValue；
- lastRecoveredAt。

它只服务事件边沿判断，不替代 `WatchTrigger` 历史；初始化、成员变动和 unknown 语义见 §5.4。

### 9.3 不引入

- 不引入 ruo 的 `SignalEvent → StockAlert → UserAlertDelivery` 三表模型。
- 不引入 Redis Streams 和单独 AlertPipelineWorker。
- 不让浏览器承担定时扫描。
- 不让前端直接保存或调用飞书 Webhook。
- 不复制一套独立于 tactic DSL 的复杂表达式引擎。

## 10. 分阶段范围

### Phase 1：可用性与可靠性

目标：用户能创建常用预警，且不会因条件持续成立被重复轰炸。

- 方案模板和自然语言草案入口；
- price-change 增加方向；
- price-level；
- `ANY` / `ALL`；
- 规则稳定 `ruleId`；
- on-enter / repeat / daily-first；
- 规则状态与 recovered 事件；
- 优先级、每日通知上限和细分送达状态；
- 预警卡片补齐行情、基准、成本和证据；
- 已处理 / 有用 / 无用反馈。

实施顺序：先落 schema 与迁移（`rules[].id`、`deliveryStatus`、`WatchRuleState`）和触发语义（on-enter / ANY / ALL），再做模板与自然语言入口，避免 UI 验证阻塞模型冻结。

### Phase 2：策略丰富与复盘

- volume-ratio、drawdown-from-high；
- 涨停、炸板、断板规则；
- 触发后 1 日 / 5 日表现（消费 [ruo 迁移文档](./ruo-feature-migration-product-design.md) Phase 3A 的 `SignalObservation`，不另建）；
- 方案级有效率和噪声分析；
- 高优先级预警一键生成结构化 advice；
- 恢复通知和静默到指定时间。

### Phase 3：外部事件与智能优化

- 新闻、热点关联、重大公告识别等非结构化低频事件源；
- 基于历史反馈给出阈值调整建议；
- 通知摘要和个性化时段；
- 在真实需求出现后再评估是否需要通用 SignalEvent。

> 排期说明：日期确定的财报、解禁、分红和手工事件不再归入本阶段；它们按
> [ruo 能力迁移产品设计文档](./ruo-feature-migration-product-design.md) Phase 1B
> 建设 `StockEvent` 和 `event-date` 规则。此处保留的是依赖内容理解或新事件数据源的扩展能力。

## 11. 验收标准

### 功能

- 用户通过模板创建一条持仓止损预警的路径不超过 4 步、必填参数不超过 2 个。
- 新建方案首轮评估只初始化规则状态，不产生 triggered；试跑可见当前命中。
- 用户可用自然语言生成草案，系统不会未经确认写入。
- 支持上涨、下跌、价格突破、价格跌破、成本止盈止损和 tactic 规则。
- `ANY` / `ALL` 行为可通过试跑明确验证。
- on-enter 模式下条件连续成立只产生一次 triggered，恢复后再次进入才重新触发。
- 同一方案的两条同类规则互不错误抑制。
- 试跑不发送、不占正式 cooldown。
- 每条触发都能看到规则、行情时间、基准值、证据和送达状态。
- 通知失败不丢失触发事实。
- 用户可标记处理和有用性。

### 可靠性

- watch 进程重启后规则状态和 cooldown 可接续。
- 行情全源失败时本轮明确失败或部分失败，不能显示为正常无触发。
- 动态分组 stale 时方案明确降级或跳过，并说明原因。
- 0 触发时仍记录成功心跳。
- 所有时间判断统一为 Asia/Shanghai。

### 安全

- 任何预警都不能调用交易能力。
- 外部通知只由服务端 adapter 发送。
- 自然语言生成只能形成待确认草案。
- AI 建议必须展示反证、风险、免责声明和有效期。

## 12. 指标

首期关注“可靠且少打扰”，不以触发数量为成功指标。

| 指标 | 定义 | 建议目标 |
|---|---|---|
| 扫描成功率 | succeeded WatchRun / 应运行轮次 | ≥ 99% |
| 预警延迟 | 行情时间到触发落库时间 | P95 ≤ 2 个扫描周期 |
| 送达成功率 | sent / requested | ≥ 98%，排除未配置通道 |
| 可解释率 | 证据和基准字段完整的触发占比 | 100% |
| 重复噪声率 | 同一事件被用户判为重复的比例 | 观察指标，样本不足不展示结论 |
| 预警处理率 | 已处理 / 已送达 | 观察指标 |
| 用户有用率 | 有用 / 已反馈 | 观察指标，样本不足不展示结论 |

## 13. 风险与应对

| 风险 | 应对 |
|---|---|
| 规则越来越多导致编辑器复杂 | 模板优先，高级规则折叠；复杂表达交给 tactic |
| ALL 条件在不同时间成立，语义模糊 | 首期定义为同一轮评估全部成立，不做跨窗口拼接 |
| 边沿状态因行情缺失错误恢复 | 数据缺失时保持 unknown，不从 active 直接切 inactive |
| 通知聚合导致紧急预警延迟 | 紧急/重要实时，普通才聚合 |
| 触发后收益统计被误解为策略胜率 | 明确展示观察窗口和样本数，不做因果表述 |
| LLM 草案生成错误 | 严格 schema、引用存在性校验、自然语言回显、用户确认 |
| A 股特殊规则数据不可靠 | 未获得可靠逐笔/涨停状态数据前不承诺炸板等实时能力 |

## 14. 已确认决策

以下决策已于 2026-07-24 确认，作为后续产品与技术设计的约束。

### D1：产品入口是否继续以“分组”为中心

决定：**继续以分组详情为主要配置入口，仪表盘承载全局运行和最近预警。**

理由：它与当前领域语言一致，也自然表达“同一组股票可以有多套提醒”。暂不增加独立一级“策略”或“预警”导航。

### D2：首期是否支持 `ALL`

决定：**支持一层 `ANY` / `ALL`，不支持嵌套。**

这是 ruo 中真实存在且用户容易理解的能力；实现复杂度可控，也能覆盖“价格突破且放量”这类高频需求。

### D3：普通预警是否默认外部推送

决定：**紧急/重要默认推送，普通默认仅记录；用户可修改。**

如果全部推送，price-change 和趋势战法很容易制造噪声，最终导致用户关闭整个系统。

### D4：是否现在引入站内已读体系

决定：**先做 handled / useful 反馈，不复制 ruo 的 read / ack / delivery 三态。**

luoome 是本地单用户产品，“是否处理”和“是否有用”比多终端已读状态更有复盘价值。等出现多端同步需求后再补 read。

### D5：触发后是否自动生成 AI 建议

决定：**不自动生成。预警卡片提供“生成 AI 建议”操作，由用户主动触发；每日摘要可以批量分析。**

这能避免高频 LLM 成本和“规则命中被包装成确定买卖结论”，也保持 advice 与 watch 的清晰边界。

正式交互约束：

- Watch Runner 只判断规则、记录触发并按通知策略送达，不调用 advice tool。
- 预警卡片原样展示条件、证据和风险方向，不直接给出买卖结论。
- 用户点击“生成 AI 建议”后，才调用 `analyze_position` 或 `analyze_stock`。
- 生成的建议必须独立展示反证、风险、免责声明和有效期。
- advice 仍不能触发任何交易能力。

## 15. 建议的下一步

1. 将 Phase 1 拆成领域模型、workflow、tool/API、Web、迁移和测试六组实施任务。
2. 先用三个黄金场景验证交互原型：
   - 全部持仓亏损 7% 时提醒；
   - 候选股突破指定价格且放量时提醒；
   - 量价背离分数达到 70 时提醒。
3. 原型确认后再冻结实体字段和迁移方案，避免 UI 尚未验证就扩张底层模型。
