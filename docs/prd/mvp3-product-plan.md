# MVP3 产品计划：决策与复盘

> 状态：首批 D0–D4 已完成本地实现与隔离验收；2026-10-04 收尾。
> 初稿日期：2026-09-30。下文基线与候选分析保留为实施前的产品决策记录。
> 基线：MVP2 已于 2026-09-28 验收通过，见[开发计划 §2.10](../development-plan.md#210-mvp-20-p0p1-收口更新至-2026-09-28)。
> 约束：[领域语言](../../CONTEXT.md)、[架构](../ARCHITECTURE.md)、[安全边界](../SECURITY.md)。
> 详细设计：[MVP3 决策与复盘](../ddd/mvp3-decision-review-detailed-design.md)（账户记录、成交事务、API、报告版本与验收）。
> 已交付范围为 Web 账户复盘、手工登记或选择已有成交、修订回看与不可通知报告补充；券商文件导入等后续候选不在本次交付中。当前操作以[用户手册 §8](../USER_GUIDE.md#8-复盘与-confidence-校准)为准；验收未连接真实外部通知或生产投资数据。

## 1. 已确认方向与产品目标

MVP2 已建立“盘后研究与计划 → 账户报告 → 盘中条件提醒 → 用户手动更新 → 次日复盘”的自动化。
用户于 2026-09-30 明确选择 MVP3 主线为**决策与复盘**。本轮沿此方向细化首版用户旅程，
研究质量扩展和日常运维体验不作为并列主线。

产品目标：**让用户能回看“当时为什么这样建议、自己实际做了什么、后来发生了什么”，并据此决定下一步需要研究什么。**

首版建议用一条完整旅程交付：**查看计划或提醒 → 记录反馈与实际成交 → 明确关联依据 → 次日与周末回看。**
成交登记服务于真实复盘，不把版本价值缩减为表单优化；反馈和结果也不直接证明建议带来了收益。

| 决定 | 状态 | 具体含义 |
|---|---|---|
| MVP3 主线 | 用户已确认 | 决策与复盘 |
| 首个闭环 | 首批已实现 | 从计划/提醒记录实际行动，并在既有复盘中回看依据与事实 |
| 主要入口 | 首批已实现 | 优先 Web，沿用计划、预警、复盘与报告入口 |
| 实际成交录入 | 首批已实现 | 手工登记或选择已有成交；券商文件导入仍属后续候选 |
| 独立决定状态 | 首批暂不承诺 | 沿用提醒反馈与 AdviceOutcome 原意；不把“继续观察”硬映射为已跟随或已处理 |

首批按后续授权的 D0–D4 范围实施；以下候选与非目标不因本次实现而自动扩大为已交付功能。

## 2. 现有基线与真实增量

| 已有能力 | 依据 | MVP3 候选增量 |
|---|---|---|
| 账户逐股计划、仓位预算、盘后报告、确定性盘中提醒与投递审计 | [MVP2 验收](../development-plan.md)、[TradingPlan](../../CONTEXT.md#逐股交易计划tradingplan) | 从当前提醒直接进入处理与记录，保留原计划版本 |
| Trade 支持实际成交时间，以及 Advice、研究假设版本和策略版本关联 | [Trade](../../packages/core/src/entity/trade.ts)、[add_trade](../../packages/tools/src/tools/add-trade.ts) | 在 Web 用可读的股票、时间和依据选择完成登记，不要求输入内部 ID |
| AdviceOutcome 支持跟随、部分跟随、忽略与交易关联；当前结果本身没有账户字段 | [record_advice_outcome](../../packages/tools/src/tools/record-advice-outcome.ts)、[AdviceOutcome](../../packages/core/src/entity/advice.ts) | 从建议或提醒选择已有成交，补齐账户归属后展示个人执行记录 |
| 触发已有“已处理 / 有用 / 无用 / 忽略”反馈 | [set_watch_trigger_feedback](../../packages/tools/src/tools/set-watch-trigger-feedback.ts) | 沿用反馈能力，明确它与实际成交、计划有效性分别是什么关系 |
| 决策闭环统计、信号 T+1/T+3/T+5 观察、账户绩效和周报 | [复盘 Tool](../../packages/tools/src/tools/get-decision-loop-review.ts)、[用户手册](../USER_GUIDE.md) | 把用户刚记录的决定与事实带入既有复盘入口，并能回到对应依据 |

代码核对发现：Web 复盘仍要求手填“关联交易 ID”；持仓成交登记未暴露 Tool 已支持的完整时间和
来源关联。这些是可验证的操作缺口；改善后是否降低日常记录负担，需在实际试用中验证。

不重复立项策略工作台、AI 策略生命周期、研究 Vault、账户绩效、报告中心或整个复盘系统。
MVP2 的数据源间歇失败继续作为运营问题跟踪，不因新版本规划改写为未验收。

## 3. 目标用户、场景和成功结果

沿用本地单用户、沪深 A 股、低频决策、用户自主执行交易的产品定位。优先服务已经使用 MVP2
计划与提醒的现有用户，不同时承担新手引导、跨市场和多人协作。

### 3.1 首个完整用户旅程

首个完整场景：

1. 用户在 Web 打开一条风险或退出提醒，看见当时的计划、行情证据、有效期和当前状态。
2. 用户按既有语义标记提醒反馈，或登记自己已经完成的成交；反馈默认不预选“跟随”。
3. 登记成交时可以选择已有记录，也可以填写真实时间、方向、数量和价格，顺序追加尚未入账的成交。
4. 新增成交按既有账本规则更新现金和持仓；账户变化后，旧计划按现有事实指纹规则失效。
5. 用户在次日报告或本周复盘中，看到当时建议、自己的记录和已知结果，能返回原始事实。

“有用 / 无用 / 忽略 / 已处理”是提醒反馈；“有成交记录”是账本事实；“未填写”保持未知。
页面已读、提醒已处理和通知渠道受理都不能代替成交证明。

### 3.2 复盘必须回答的三个问题

| 用户问题 | 首版展示 | 必须保留的限制 |
|---|---|---|
| 当时为什么这样建议？ | 当时的计划/Advice、关键条件、支持与反对证据、风险、数据时间和有效期 | 回看原版本；当前新计划不能覆盖当时依据 |
| 我实际做了什么？ | 用户显式反馈、关联的成交时间/方向/数量/价格，以及未关联记录 | 没有记录显示“实际行动未知”；反馈不自动变成成交，成交也不自动判定完全跟随 |
| 后来发生了什么？ | 已有信号后续行情、用户填报结果、账户绩效分别展示，并能查看事实来源 | 行情观察不等于实际盈亏，账户收益不等于单条建议效果，样本不足不评价策略优劣 |

例如，一条减仓提醒后，用户关联了两笔卖出，但仍保留部分持仓：复盘展示原减仓依据、两笔
实际成交和剩余持仓状态；“部分跟随”仅在用户明确记录后展示。不能因为股价随后下跌，就自动
填入“避免亏损金额”或宣称该提醒成功。原始行情、成本或关联不足时，结果保持未知。

建议的回看节奏：次日侧重核对昨天的计划、提醒和已登记行动，周末侧重有依据地回看变化、
缺失记录和待研究问题。两者复用已有报告；不要求每条建议每天手工填写盈亏。
复盘发现应能回到原始记录，例如某个入场前提后来是否仍成立、哪些决定缺少记录；下一步可以是
核对事实或主动重新研究，不因一两次盈亏自动修改策略。

## 4. 建议范围

### 首批必须明确的事实归属

- 用户的采纳、忽略、成交关联和填报结果必须归属明确账户；切换账户不能覆盖或复用另一账户的执行记录。
  现有 AdviceOutcome 以 Advice 为身份且没有 `accountId`，不能把旧结构直接当作账户级决策记录。
  这是首批详细设计必须补齐的契约；存量无法确定账户的反馈显示归属未知，不猜测迁移。
- 行情观察只有存在明确来源链时，才能附在对应提醒/建议下。现有 SignalObservation 主要引用
  WatchTrigger 或 StrategySignal，不是每条 Advice 都有观察；仅因同股就匹配的结果不能展示为该建议效果。
  观察本身可共享，用户执行记录按账户区分。

### P0-A：从提醒到决定的连续入口

- 在现有预警、计划详情及报告入口补齐处理入口，不另建一套通知系统。
- 同时显示触发时的计划版本和当前有效性；过期、被替代或账户变化的提醒仍可用于历史记录，
  不能呈现为当前有效操作建议。
- 支持记录反馈、查看已有记录、进入成交登记或主动重新研究。既有提醒反馈与 AdviceOutcome
  各自保持原意，不相互自动映射。独立的“继续观察 / 暂不采纳”决定及原因属于候选语义增量，
  是否纳入须先由产品讨论确定，不留给详细设计自行映射，首批暂不承诺。
- 用户记录提醒反馈不会暂停风险监控；处理一条提醒不会静默关闭后续新的风险事件。
- 对同股多条提醒展示明确来源，不能因列表合并丢失风险、证据或版本身份。

### P0-B：可理解的成交登记与显式关联

- 从提醒或 Advice 进入表单时预填账户、股票和来源上下文；成交价格、数量、时间由用户确认，
  不把建议价格或行情价格当成实际成交。
- 支持填写真实成交时间，以及从本账户同股记录中选择已有成交；不再要求手输交易 ID。
- 允许自主交易不关联建议；补充历史成交的来源关联时，不强制关联当天最新计划。多条可能依据必须由用户选择。
- 首批新增成交限于顺序追加、尚未由持仓或资金调整体现的实际成交。任意插入旧交易、重排历史
  买卖或补录已经体现在持仓中的成交，会涉及成本重算和重复入账，暂不承诺；应给出明确的核对提示。
  当前 Tool 接受成交时间并不意味着支持历史账本重放，冻结前须明确入口校验与拒绝边界。
- 关联保留触发、确切计划版本和 Advice 的可追溯关系；多 Advice 来源不得任取一条归因。
  具体使用已有引用还是增量关系，留给详细设计；不在产品稿中预设新实体。
- 选择已有成交只增加关联，不重复修改账本；新增成交与关联的失败必须可恢复且不重复记账。
  重复点击、刷新重试和多笔部分成交是验收场景。
- 更正关联保留可追溯记录，不修改不可变的原计划或主报告。交易本身的撤销、冲正流程是否扩展，
  单独评估，不混入本次来源关联功能。

### P0-C：在既有复盘中看清“建议—决定—事实”

- 每条复盘以 §3.2 的三个问题组织内容；打开记录即可查看原始依据、实际行动和结果状态，
  无须在计划、交易流水和报告之间手动比对内部 ID。
- 次日复盘和周报分别列示计划与提醒、用户反馈、已登记成交、可用结果及缺失信息。
- 所有统计可以回到具体记录；账户和时间范围明确，区分成交发生时间与补充关联时间。
- 用户自报的跟随与盈亏、已关联成交、账户整体绩效和信号后续行情分别标注口径。
  未平仓、部分平仓或缺成本时，不新造一套单条建议收益归因算法。
- 同一成交被多条研究依据引用时，账户成交与盈亏不能重复累计；多来源只说明关联，不证明因果。
- 给出待补记录和可继续研究的入口；反馈本身不改变 Strategy、仓位限制或盘中提醒规则。
  已有显式启用的策略自动化政策继续按原契约运行。
- 补充反馈或关联后生成的报告遵守 MVP2 不可变主版与补充版本规则，不追写历史结论。

### 后续候选，不进入首批交付

- 券商成交文件导入：仅在手工登记被确认是主要负担后，再选一种真实文件格式，设计字段映射、
  预览、重复检测与撤销；现有 luoome JSON 数据恢复不等于券商流水导入。
- 账户偏好：投资目标、风险偏好和提醒节奏需独立确认，不在本稿中改变总仓位 100%、单股 30%
  的现有默认值，也不恢复已取消的行业预算限制。
- 运行状态汇总：只有日常排查确实需要时，再把已有数据源、盘后批次、监控和投递审计合并为用户入口。

## 5. 继续保持的产品边界

- 沿用仅行情数据的 MVP2 研究范围；新闻、公告、真实财务 PIT 与严格回测扩展需另行立项。
- 不接入券商下单，不把登记实际成交变为发出订单；不增加任何自动交易路径。
- 盘中继续按计划条件确定性求值；不恢复盘中 AI 自动改写计划。
- 保留反证、风险、免责声明和有效期；缺失事实显示 unknown/unavailable，不以零值补齐。
- 写入沿用显式能力开关与账户范围校验；Web、CLI、MCP 通过同一 Tool 契约消费能力。
- 本轮优先 Web 入口，兼顾现有响应式页面。飞书移动端跳转本地服务的可达性不作默认承诺，
  不因此扩展云同步、远程访问或原生移动应用。

## 6. 验收场景与评价方式

以下为建议验收口径，具体范围确定后随 PRD 冻结：

| 场景 | 可观察的完成标准 |
|---|---|
| 用户记录提醒反馈 | 能在复盘找到原意一致的反馈；不新增 Trade、不改变现金或计划监控资格 |
| 用户登记一笔实际成交 | 从提醒进入并完成来源关联，不输入内部 ID；账本只变动一次 |
| 用户选择已有成交 | 能按股票、时间、方向和数量识别记录；关联前后现金与持仓不变 |
| 提醒已经过期或被新计划替代 | 当前状态清楚；仍可补充反馈或关联已有成交；不误导为当前有效建议 |
| 同股多条依据、部分成交与重复提交 | 显式保留所选依据，多笔成交可关联；不重复记账或累计收益 |
| 只有反馈，没有成交或盈亏 | 显示自报/未知；不把“没登记”统计为“没执行”或亏损 |
| 未采纳、部分成交或尚未平仓 | 用户声明、真实成交和后续行情分开；不自动输出跟随结论、假想盈亏或成功标签 |
| 跨账户、跨日补充关联与报告补充 | 不串账户；沿用成交原始事实时间；原计划和主报告保持原样 |
| 两个账户引用同一股票建议 | 一个账户回填结果不覆盖另一个；无法归属的旧反馈不算作任何账户的执行事实 |
| 同股存在多个信号但建议没有明确观察来源 | 显示缺少关联观察，不拿其它信号涨跌替代该建议的结果 |
| 乱序历史交易或已在持仓中体现的成交 | 不以新增交易直接重复写入；解释需核对的原因，不假装成本可正确重算 |
| 无写权限或关联保存失败 | 读取仍可用，写入失败可解释；恢复后不会重复产生账本变动 |

产品效果先测任务完成度，再观察使用行为：

- **主要验收**：上述用户旅程能在真实浏览器完成；不依赖 CLI、复制 ID 或直接改库。
  用户能从一条复盘中找到当时依据、自己的实际记录和已知/未知结果，而不仅是完成一次表单填写。
- **效率观察**：记录“打开提醒 → 保存反馈/成交”的步骤数与耗时，比较改动前后；先测基线，
  不凭空承诺固定节省比例。
- **闭环观察**：分别展示待记录事项、显式关联成交数 / 已登记成交总数、用户反馈数 / 可反馈提醒数。
  分母为零显示无样本；自主交易无须为了提高关联率而强行绑定建议。
- **质量底线**：重复记账、跨账户关联、未知盈亏被填零、已处理被当成交、历史主版被覆盖，在验收场景中均为零。
- 不以短期收益、AI 调用量或聊天轮数验收 MVP3；少量样本只能证明流程可用，不能证明投资效果。

## 7. 交付顺序

| 阶段 | 可评审产物 | 进入下一阶段的条件 |
|---|---|---|
| 0：选择主线（已完成） | 用户于 2026-09-30 选择“决策与复盘” | 已进入范围细化；不再重新选择版本方向 |
| 1：冻结产品契约 | 用户旅程、页面草图、账户归属、状态含义、关联与纠错边界 | 明确首批录入方式与范围；区分已复用能力和确切增量 |
| 2：首个完整切片 | 一条计划/提醒 → 选择已有成交或新增未入账成交 → 明确依据 → 复盘回答三个问题 | 隔离账户完成正常、重复提交、失效计划和失败恢复场景 |
| 3：反馈与报告收口 | 既有反馈入口、来源多义、部分成交、报告补充 | 全部验收场景通过；Tool 与各入口语义一致 |
| 4：实际试用 | 用户日常操作与问题记录 | 用户确认入口可用；真实结果缺失仍如实保留 |

Web 变更须实际启动并用浏览器验收；如新增存储，双仓储和合约测试同步。
本轮不估承诺发布日期；在范围冻结后再拆开发任务和工期，不以固定等待天数替代可复现验收。

## 8. 尚待用户决定

当前最影响范围的是**实际成交如何进入系统**：

| 选择 | 对首版范围的影响 |
|---|---|
| 手工登记或选择已有成交（建议） | 先打通已设计的完整旅程，复用现有账本 |
| 券商成交文件导入 | 需要一种明确文件格式，并增加预览、映射、去重和账本一致性边界 |
| 只更新持仓，暂不逐笔登记 | 可先做计划、反馈和持仓变化回看；成交时点、真实执行与单条建议盈亏不能据此推断 |

未收到录入方式选择前，暂按第一项继续讨论。独立决定状态、券商导入和单条建议收益计算不因
“决策与复盘”主线确认而自动加入首批范围。
